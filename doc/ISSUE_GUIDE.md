# 怎么发 Issue（Issue 操作指引）

> 本文件是仓库内所有 Agent 与协作者的 issue 规范，**必须遵照执行**。
> 配套：怎么开 PR 见 [PR_GUIDE.md](PR_GUIDE.md)；流程总览见 [AGENTS.md](../AGENTS.md) §「迭代流程」。

## 定位：issue 是最小执行单元

- 一个 issue = 一件可以独立交给一个会话、独立验收、独立关闭的事。
- **先立单再动手**：发现缺陷（写代码时、审 PR 时、跑门禁时都算）当场立单，不需要先问、不需要攒批。issue 是执行与验收的唯一依据；「我觉得这里有问题」不落成带证据的 issue，就等于没发生过。
- 立单**不属于**「改代码」：提完就可以停，修复另开一次执行。

## 什么时候开

| 场景 | type | 建议 label |
|---|---|---|
| 功能坏了、行为不符合预期 | `bug` | `bug` |
| 门禁/测试自身有缺陷（误报、漏报、环境依赖） | `bug` 或 `fix` | `bug` |
| 新功能 / 新能力需求 | `feat` | `enhancement` |
| 清理死代码、构建配置等杂务 | `chore` | — |
| 重构（不改外部行为） | `refactor` | — |
| 测试体系增补 | `test` | — |
| 文档新增/修订、实机验证回填 | `docs` | `documentation` |
| 协作规范 / 流程约定 | `[规范]` | `documentation` |
| 缺口总账（对照某份报告逐项盘点） | `[追踪]` | `enhancement` |
| 合并态快照、落地汇总、实机验证结果 | `[记录]` | `documentation` |
| 可行性 / 调研报告，作为后续 issue 的引用源头 | `[存档]` | `documentation` |
| 审计发现（泄露、缺陷复核） | `Audit` | `bug` |

## 标题规范

```
type(scope): 一句话摘要
```

- 摘要说清「什么坏了 / 要什么」，扫列表就能读懂项目状态；不写「有个问题」。
- `scope` 标子系统（`metadata` / `export` / `album` / `ci` / `agents` / `xmp`…），可省。
- 同根因复发时标题带上一代编号（如「#4 的第二例」），并互相引用。
- 真实示例：

| 标题 | 要点 |
|---|---|
| `feat(metadata): 常用手动镜头快捷预设改为用户自定义`（#4） | 说清改哪块、改成什么 |
| `[规范] 迭代流程对齐 IdleJot：issue → plan → worktree → PR → 对账回签`（#6） | 规范类用方括号类型，正文即规范 |

## 正文四要素（缺一不可）

### 1. 现象

行为类 issue 的现象段必须交付**一条可直接粘贴执行的复现命令**，外加期望输出、实际输出与触发条件：

| 字段 | 要求 |
|---|---|
| 复现命令 | 一条，能整段粘贴（`npm run e2e:render` / `cargo test --lib <名字>` / 具体的点击路径）。跨多步的先归并成单行或一个可整段粘贴的代码块 |
| 期望输出 | 正常时应看到什么 |
| 实际输出 | 现在看到什么，贴**原文**（错误文案、返回码、截图路径） |
| 触发条件 / 频率 | 什么环境、什么条件下触发；偶发写「出现次数 / 总次数」，必现直接写必现 |

- 非行为类（纯文档、纯重构、纯规范）写 `复现命令：无（不涉及运行时行为）`。
- 反例：「有时候会失败」「感觉不太对」——无法复现的一律先贴 `needs-repro`。

### 2. 证据链

- 每条判断都要有 `文件:行号` 或可复现命令；日志给路径与关键行。
- **无证据不修复**：没有证据的 finding 视为虚构，直接退回。
- 项目注释密度高，「为什么」大多写在代码旁边；引证据时连注释一起引，别只引一行代码。

### 3. 影响面

- 谁受影响（哪条链路 / 哪个视口 / 哪个导出路径）、什么条件下触发、严重度用 **`P+数字`**：`P0` 阻断（数据损坏、导出错误、主链不通）/ `P1` 常见路径 / `P2` 边角与增强。
- 修复顺序在 issue 里定，不在实施时定。
- 一件事装不下的大 issue：先定**分节（`P+字母`）**再拆——一个分节 = 一个可独立合并的 PR，命名规则见 [PR_GUIDE.md](PR_GUIDE.md)「拆分与命名规范」。

### 4. 修复候选 + 回归建议

- 给出建议方向（不要求完美），并明确**用什么测试/门禁钉住复发**。
- 每个被修的缺陷都应留下「墓碑」：能红的用例 + 注释写明防哪个 issue 复发。

## 写 plan：追评到 issue 下面（实施前必做）

issue 立完之后、动代码之前，**把 plan 追评到 issue 评论里**（不是写进 issue 正文、不是写进 PR）。issue 是执行与验收的唯一依据，plan 是它下面的第一层执行证据。

| 要素 | 要求 |
|---|---|
| 验收基线 | 必有一行：`用 issue 的复现命令复现：成功 / 失败（贴原始输出）`。**复现失败说明描述与现状不符，退回发现者补充，不进实施。** |
| 探索结论 | 每条带 `文件:行号` 或可复现命令；说清「现状为什么是这样」，不只说「要改成那样」 |
| 方案 | 按落点列（分节用 `PA`/`PB`…），每节能独立合并 |
| **明确不做** | 列出评估后决定不做的项**与理由**；不写这一项，评审无法区分「漏了」与「故意不做」 |
| 验证方式 | 用什么命令 / 用例 / 变异证明做完了 |

**定稿后只追加不改口**：plan 有变就再追一条说明改了什么、为什么改，不回头编辑原评论——否则对账时无法判断执行是否偏离过计划。

```markdown
## plan 追评（<日期>）

**用 issue 的复现命令复现：成功 / 失败。** 原始输出：

```
<粘贴命令与输出>
```

### 探索结论（带证据）

1. `src/...:42`：<该处说明了什么>

### 方案

| 分节 | 落点 | 内容 |
|---|---|---|
| PA | `src/...` | <做什么> |

### 明确不做

- <不做项>：<理由>

### 验证方式

- 用例：<命令>
- 变异：<改坏哪个子串必须让哪条用例红>
```

## 复现命令与 `needs-repro`

- **发现者**：给不出可粘贴的复现命令就贴 `needs-repro`，不要硬写「有时候会」。补齐后摘标签；确实不可复现（时序、外部服务、权限）就写清为什么，由维护者决定是否降级为观察项。
- **修复者**：写 plan 时必须先回填一行验收基线——`用 issue 的复现命令复现：成功 / 失败（贴原始输出）`。**复现失败说明描述与现状不符，退回发现者补充，不进实施**。
- **回签**：合并后用同一条命令再跑一次（见下节）。

## 关闭：行为类靠回签，不靠合并

issue 的关闭点跟着「验收」走，不跟着「合并」走：

- 纯文档 / 纯重构 PR 用 `Closes #NN`，合并即关闭。
- 行为类 PR（`fix` / `feat` / `perf`，以及任何改运行时代码的 PR）用 `Refs #NN`；合并后 issue 保持打开并贴 `needs-live-verify`，等回签。
- **回签**由发现者（或全新上下文的验证会话）执行，按 [PR_GUIDE.md](PR_GUIDE.md)「合并后：对账与回签」的模板贴复现命令、实际输出与实机证据。结论为「症状消失」才摘标签并关闭。**修复者不能给自己回签。**

> 注意区分两个「全新上下文」职责：**合并评审**（PR 合并前，决定合不合，见 [PR_GUIDE.md](PR_GUIDE.md)「合并评审」）和**回签**（PR 合并后，决定 issue 关不关）。两者都由 subagent 承担，但一个盯 diff 与门禁，一个盯实机复现。

## 记录三件套（用 issue 做项目记忆）

| 类型 | 用途 |
|---|---|
| `[记录]` | 合并态快照：某阶段落地汇总 + 实机验证结果，后续 issue 的现状基准 |
| `[存档]` | 可行性 / 调研报告：结论与风险清单，被后续 issue 引用为源头 |
| `[追踪]` | 缺口总账：逐项列「已做 / 未做 / **评估后建议不做并终结**」，防止同一缺口被反复重开 |

实机验证结果不写进 issue 长文，用 docs PR 回填仓库文档（`docs/` 或 `.plan/`），issue 里只留结论与链接。

## 反模式

- 一个 issue 塞多件事——无法独立关闭。
- 只有结论没有证据——按「证据链」退回。
- 把 issue 当聊天记录 / 进度播报——过程写 PR 评论，结论写 issue。
- 修完直接推 `master`——必须走 PR。
- 行为类 issue 用 `Closes` 合并即关——症状没被复现命令验过，关闭只是修复者的自述。

- 触发条件 / 频率：<环境 / 条件 / 偶发或必现；非行为类写「无（不涉及运行时行为）」>
