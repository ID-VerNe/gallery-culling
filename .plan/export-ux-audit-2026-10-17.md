## 2. 发现汇总（按严重性排序）

### Major（严重性 3）— 3 条

#### E-02 — 「★ 3 星以上」会把已淘汰的照片带出去

**证据**：`src/components/export/exportFilters.ts:43-46`

```ts
{ value: 'star3_plus', label: '★ 3 星以上', test: (g) => g.rating >= 3 },
```

同文件 `:27` 的注释是这一族的**契约声明**：

> `all` 显式排除淘汰（reject）—— 淘汰是用户的删除意图，绝不能因为「全选」被导出。

而 `:35` 的 `pick_or_rated` 里恰好有一道守卫：

```ts
test: (g) => g.flag !== 'reject' && (g.flag === 'pick' || g.rating > 0),
```

这道守卫是**载荷**而非冗余：`rating > 0` 对一张被淘汰的照片完全可能为真
（`rating` 与 `flag` 是独立字段，`CullFlag = 'none'|'pick'|'reject'`，
见 `src/types/index.ts:21`）。作者在 `pick_or_rated` 里防住了这个组合，
**在 `star3_plus` 里漏了同一道守卫**。

**测试把这个行为写成了注释**：`src/hooks/useExportForm.test.ts:49`

> `D：reject + 3 星 → 只在 star3_plus（淘汰永不被「全部」「仅含 RAW」带出）`

括号里刻意只提了「全部」和「仅含 RAW」，没提 `star3_plus`。`:106` 的断言
`toEqual(['B', 'D'])` 里，`D` 就是那张 `flag: 'reject', rating: 3` 的照片。
**测试没有抓错，它把这个不一致锁成了既定行为。**

**后果**：用户判了死刑的照片，换个范围档就能被导出。`pick_only` 不受影响
（`flag === 'pick'` 与 `'reject'` 互斥），只有 `star3_plus` 漏。

**修法**：`test: (g) => g.flag !== 'reject' && g.rating >= 3`，并把 `:49` 的注释
与 `:94` 的 `star3_plus: 2` → `1`、`:106` 的 `['B','D']` → `['B']` 一起改。

#### E-03 — 主按钮禁用时不给任何理由（校验文案写了但永不显示）

**证据**：`src/components/BatchExportModal.tsx:142`

```tsx
disabled={isExporting || !form.canRun}
```

`form.canRun` 来自 `validation === null`，而 `buildValidationMessage`
（`exportMessages.ts:126-143`）有 5 种返回。UI 里**只渲染了其中 1 种**：

`BatchExportModal.tsx:187-191` —— 只有 `targetIsSourceDir` 时才把文案画出来。
其余三种静默：

| 触发条件 | 文案（已写好，从不显示） |
|---|---|
| 目标目录为空 | 请先选择导出目标文件夹。 |
| 候选为 0 | 当前导出范围内没有照片，请先给照片打星或标记保留。 |
| 两种文件类型都没勾 | 请至少勾选一种要复制的文件类型。 |

（第 5 种 LUMEN 不可用有 `LumenGateNotice` 常驻兜底，不算静默。）

**并且 `handleExport` 里的兜底是死代码**：

```tsx
// BatchExportModal.tsx:74-77
if (form.validation) {
  onError?.(form.validation);   // 永远走不到：按钮在 validation 非空时就是 disabled
  return;
}
```

注释写着「按钮的 disabled 与这里的提示同源……不会出现『能点但点了报错』」——
这句话是对的，但代价是**提示本身也没了**。

**后果**：首次使用者最常撞的墙是「没打星 → 默认范围 0 张 → 灰按钮 → 零解释」。
把 RAW 和 JPG 两个勾都取消，也是同样的死胡同。用户只能猜。

**修法**：把 `validation` 常驻渲染在 footer 主按钮左侧（或按钮下方），
`aria-describedby` 挂到按钮上。不要用 Toast——那是事后反馈，
这里需要的是**持续可见的原因**。

#### E-05 — 同名文件一律跳过，没有覆盖入口（成片模式的迭代工作流被卡住）

**证据**：`src-tauri/src/commands/export.rs:66-70`

> 本项目**从不覆盖**目标同名文件（一律 skipped）

`:162-171` 是判定点。UI 侧只有一句事后说明
（`exportConfig.ts:71` `skipNote: '目标已存在同名成片'`）。

**后果**：调色成片的自然工作流是「调 → 导出 → 看 → 再调 → 再导出」。
第二次导出会**全部 skipped**，目标目录里躺着上一版的成片，用户拿到的不是刚调的。
UI 既没有「覆盖已有文件」的勾选，也没有「换一个目录」的引导。

这不是 bug（不覆盖是保护用户文件的正確选择），是**缺一个显式出口**。
对复制模式影响小（原片不会变），对成片模式是每次迭代都要手动清目录。

**修法**：加一个 `覆盖同名文件` 复选框（默认关），后端 `dst.exists()` 分支
改成按参数决定 `skipped` 还是走临时文件 + rename 覆盖。或者退一步：
skipped > 0 时在结果条里给「打开目标目录」按钮，让用户自己去清。

### Minor+（严重性 2）— 6 条

#### E-01 — 「仅含 RAW 的组」这个标签是错的

**证据**：`exportFilters.ts:48-56`

```ts
label: '仅含 RAW 的组',
test: (g) => g.flag !== 'reject' && !!g.raw,
```

谓词是「**含** RAW」，标签说的是「**仅含** RAW」——「RAW 且没有 JPG」。
用项目自己的测试 fixture 就能证明标签是假的：`useExportForm.test.ts:33`
无条件给每组挂 `jpg`，`:36` 才按 `hasRaw` 挂 `raw`；而 `:113` 断言
`raw_only` 返回 `['A','B','C']` —— **这三组每一组都同时带 JPG，没有一组是
「仅含 RAW」**。

**后果**：选这档的用户以为筛掉了带 JPG 的组，实际没有。计数（11 vs 想象的 4）
对不上，用户会怀疑筛选没生效。实际导出的**文件**是对的（复制模式只勾 RAW 就只拷 RAW），
所以是认知成本，不是数据错误。

**修法**：改标签为「含 RAW 的组」或「有 RAW 原片的组」。四个字，消除歧义。

#### E-04 — 导出范围忽略左侧筛选与多选

**证据**：`App.tsx:633` 传的是 `groups={groups}`（全部照片）。

对照同文件 `:136-138` 的批量评级：

```ts
const batch = useBatchOps({ filteredGroups, selectedIds, ... });
```

`useBatchOps` 的语义是「有选中就作用于选中，否则作用于筛选集」。
**同一个应用里存在两套「批量作用于谁」的语义**，而导出弹窗对此没有任何说明。

**后果**：用户 Ctrl 选 5 张、或在左侧筛到 3★以上，点「导出」看到的是全部照片的
候选计数。他得自己意识到「这个弹窗不认我的筛选」。

**修法**（二选一，都比重构便宜）：
1. 弹窗顶部加一行说明：「导出范围基于全部照片，不受左侧筛选与多选影响」；
2. 更好的：给 `groups` 之外再传 `selectedIds` / `visibleGroups`，在「导出范围」
   里加一档「已选中的 N 张」，有选中时默认选它。

#### E-06 — 失败明细 3 条封顶、不可展开；清单文件对用户不可见

**证据**：`exportMessages.ts:32` `FAILURE_DETAIL_LIMIT = 3`，`:72-76` 用
`slice(0, 3)` + 「等」收尾。

后端其实写了完整的 `.gallery-export.json`（`export.rs:110` 清单文件名，
逐项 `copied|skipped|failed|cancelled` + `error`）。**前端零引用这个文件**
（全仓 grep 只在 `e2eRunner.ts` 的注释里出现过「清单」二字，那是测试对账用）。

**后果**：50 张失败时用户只有 3 条原因 + 「等」，而完整清单就在目标目录里、
却没有任何一处告诉他存在。这是把已经做好的诊断数据藏起来了。

**修法**：失败时结果条末尾加一行「完整清单：目标目录下的 `.gallery-export.json`」，
或直接给个「复制失败列表」按钮。

#### E-07 — 「组 / 个 / 张」三套数量口径并存

**证据**：

| 位置 | 显示 | 单位含义 |
|---|---|---|
| footer `BatchExportModal.tsx:121-127` | 预计导出 **11** 组照片 | 照片**组** |
| 进度 `export.rs:396` | 3 / **11** | 照片**组** |
| 结果 `export.rs:243` `exported += 1` | 已导出 **18** 个 | **文件**数 |

`exportConfig.ts:28` 的 `unit: '个' | '张'` 是文件级单位，`estimateUnit` 是组级单位。
复制模式下 1 组 = 1~2 个文件（RAW + JPG），所以「预计 11 组 → 已导出 18 个」
这两个数**永远对不上**，中间也没有一句话解释为什么。

成片模式反而是一致的（组=张，一组出一张），所以这个问题只在复制模式出现，
更容易被当成偶发。

**修法**：要么 footer 也说「预计导出 11 组（约 22 个文件）」，要么结果句改成
「已导出 18 个文件（来自 11 组）」。**同一屏内的数字必须能互相验算。**

#### E-08 — 「关闭」按钮的禁用理由只存在于 `title` 属性

**证据**：`BatchExportModal.tsx:131-135`

```tsx
title={isExporting ? '导出进行中：请等待完成或点击「取消」，关闭不会停止导出' : undefined}
```

键盘用户与读屏用户拿不到 `title`；触摸设备没有 hover。禁用态本身对读屏只播
「不可用」，不播原因。

**修法**：导出进行中时把这句话直接渲染成可见文本（进度区已经有一块地方），
或给按钮加 `aria-describedby` 指向一个 sr-only 说明。

#### E-09 — 导出完成后没有「打开目录」出口

**证据**：结果条只有一句纯文本路径（`exportMessages.ts:79` 末尾
`（目标：${targetFolder}）`）。全弹窗没有第二个与目标目录相关的可操作元素。

导出完成后的下一个动作，几乎 100% 是「去看文件」。桌面应用里这是标准动作。

**好消息：这个修复很便宜。** `src-tauri/capabilities/default.json:12` 已授
`opener:default`，`api.openInDefaultApp` 已存在，Windows 分支走
`cmd /c start "" <path>`（`src-tauri/src/commands/apps.rs:43-45`），
**传目录会直接打开资源管理器**。缺的只是一个按钮。

（技术注意：`cmd /c start` 拼接路径有引号/特殊字符风险，这是既有实现的问题，
加按钮前建议先确认路径含空格与 `&` 时的行为，或改用 `opener` 插件的 `open_path`。）

#### E-10 — 质量输入越界后被静默改写

**证据**：`useExportForm.ts:177-180` + `exportConfig.ts:98-101`。

## 4. 前三条为什么必须修（不是洁癖）

- **E-02** 是唯一一条「用户明确表达过意图，程序却违背」的问题。导出是写盘操作，
  信任成本最高。一个「淘汰」标记被绕过，比十处文案不清更伤。
- **E-03** 是唯一一条会让用户**卡住且不知道原因**的问题。其它问题都是「做得不够好」，
  这条是「做不下去」。
- **E-05** 是唯一一条让**重复劳动**的问题。调色师每天要导出十几轮，
  每轮都要手动清目录。

## 5. 良好实现（确认无需改动，避免误伤）

以下是我特意验证过、确认**不是**问题的地方——修上面那些时别顺手改坏：

1. **结果绝不伪装成功**：`exportMessages.ts:79` 部分失败用 `partialTitle`，
   `failedCount > 0` 决定 `role="alert"` vs `role="status"`
   （`ExportResultPanel.tsx:27-46`）。语义分工正确，不是样式偏好。
2. **取消 ≠ 失败**：`exportMessages.ts:52-58` 单独分支，且 `toast: null`
   不重复弹窗。后端 all-or-nothing（取消即目标目录零成片），文案说的是
   「未产生任何文件」，可验证。
3. **进度播报节流**：`TaskProgressBar.tsx:66-78` 只在跨 10% 档位时更新
   live region，不会把读屏用户淹没。这是很多项目做错的地方。
4. **提示不抢 live region**：新加的二次压缩提示刻意不声明
   `aria-live`（`RenderOptions.tsx:130-140`），与进度条/结果条不打架。
5. **目标目录护栏**：`useExportForm.ts:165-174` 用 `normalizeDir` + `parentDirOf`
   判同目录，五种路径写法（正/反斜杠、尾斜杠、大小写）都有测试
   （`useExportForm.test.ts:139-146`）。这条防的是 `fs::copy` 同路径截断原片。
6. **质量输入不做实时夹取**：`useExportForm.ts:213-215` 只在失焦时规整，
   保住了「输入 9 想打 92」的中间态。这是对的（E-10 只针对改写后不告知）。
7. **弹窗焦点管理**：`Modal.tsx:107-133` 打开聚焦 body 首个可聚焦元素（跳过右上角 X），
   关闭归还焦点，Tab 陷阱 + 弹窗栈只让栈顶响应 Esc。
8. **模式切换不丢已填内容**：`setMode` 只 bump `resetSignal`，不动
   `targetFolder` / `filter`。用户来回比较两种模式不会重填。
