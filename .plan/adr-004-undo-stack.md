# ADR-004：多步撤销用「命令栈」，批量操作算一步

- 日期：2026-10-18
- 状态：已采纳（主体落地；外部改动检测待补，见「明确不做」）
- 相关：报告 `docs/lumen-benchmark-2026-10-18.md` §5.3、FR-04；ADR-002（写盘合并）

## 背景

原实现是 `useRatingUndo`：一个最多 5 层的 `RatingSnapshot[]`，每层只装**一张**照片的旧值。三个问题：

1. **批量只留下最后 5 张。** `runBatch` 逐张 `rememberRating`，200 张批量写完后栈里只剩最后 5 张。用户按 5 次 Ctrl+Z 只回退 5 张，剩下的 195 张再也回不去 —— 而批量操作恰恰是最需要撤销的场景。
2. **没有重做。** 撤销即丢弃，误按一次就只能重做一遍操作。
3. **深度不足。** 5 步在「快速连按淘汰」的选片节奏里很容易触底。

## 决策

### 1. 命令是撤销的最小单位，不是照片

```ts
interface CullCommand {
  summary: string;            // 「淘汰 3 张」
  items: CullItem[];          // 一次操作涉及的全部照片
}
interface CullItem {
  id: string; path: string;
  before: MetaState; after: MetaState;   // { rating, flag, label }
}
```

撤销弹出一条命令，回退它的**全部**条目。批量因此天然算一步：`runBatch` 只 `pushCommand` 一次，`items` 装整批。

**取消语义**：`items` 只装「真正进入写盘流程」的照片。中途「跳过剩余」时，没碰过的照片不进命令 —— 否则撤销会把它们"恢复"成一个它们从未改变过的旧值。

### 2. 同照片连续改动仍然合并

连按 `1..5` 时用户要的是「撤销这轮改动」，不是退一格。合并条件收紧到三条同时成立：

- 栈顶存在；
- 栈顶与本次**都只有一个条目**；
- 两者 `id` 相同。

批量命令永不参与合并 —— 否则「撤销整批」会被随后的一次单张操作悄悄改写。

### 3. 撤销 = 挪到重做栈，新操作才清空重做栈

`undo()` 把命令从撤销栈移到重做栈，`redo()` 反向。`push()` 清空重做栈（分支后不能重做旧路径）。空命令（`items` 为空）直接忽略，不占步、不清重做栈。

### 4. 深度 50

报告验收线是 ≥20 步。取 50 与 §5.3 建议的环形缓冲一致，且一次批量只占一步，足够覆盖一整轮初选。超限淘汰最旧。

### 5. 状态存 ref，state 只镜像按钮态

撤销是命令式操作，调用方需要**同步**拿到命令（`take` 之后立刻写盘）。栈放 `useRef`，`useState` 只存 `{canUndo, canRedo, undoSummary, redoSummary}` 四个值，避免每次按键都重建整条命令数组。

### 6. 撤销的写盘一律 `coalesce=false`

撤销是一次确定的回填，用户不会再连按同一个键。等 400ms 静默窗口只会在批量撤销时把 200 张的收尾拖长。

### 7. 整条命令只弹一次错误

批量撤销 200 张若逐张 `reportRatingFlagError` 会刷屏。首条失败仍走既有文案（保持"界面有效、未同步 XMP"的承诺），其余只打角标，末尾补一句「另有 N 张未能落盘」。

## 明确不做（本轮）

- **外部改动检测**（报告要求的「撤销前检查 sidecar mtime，被别的程序改过要提示」）。需要新增后端命令读取 sidecar 状态、在命令里记录「我们以为磁盘是什么」、再加一个确认对话框。属于独立一块，作为 FR-04 的第二步。
- **调色进同一栈**。`before/after` 是 6 个浮点数，纳入后栈的语义会变复杂；报告 §5.3 建议等评级/旗标稳定后再评估。
- **撤销栈持久化**。进程内栈，重启即空。

## 验收用例索引

`src/hooks/useCullUndo.test.tsx`（10 条）
1. 初始两个栈都空，摘要为空串
2. push 后 undo 取回该命令，并转入重做栈
3. redo 把命令送回撤销栈，可以反复往返
4. 新操作清空重做栈
5. 同一张照片连续改动合并成一步：before 最早、after 最新
6. 不同照片不合并，各自占一步
7. 多条目命令（批量）整体算一步，不与单条命令合并
8. 深度上限 50：超过后淘汰最旧的一步
9. 空命令被忽略（不占步、不清重做栈）
10. clear 同时清空两个栈

`src/hooks/useBatchOps.test.tsx`（新增 3 条）
- 整批只压一条命令：`items` 三张、`summary` 为「淘汰 3 张」、before/after 成对
- 清除批量的 `after` 是 0 星 + 未标记，色标不动
- 中途跳过剩余：命令只含已处理的照片

`src/App.undo.test.tsx`（新增 5 条）
- 改三张不同照片后 Ctrl+Z 逐层回退
- Ctrl+Shift+Z 重做
- Ctrl+Y 同样触发重做
- 撤销后做新操作 → 重做栈清空、按钮禁用
- 底栏摘要可读（`撤销：标记为淘汰` / `重做：标记为淘汰`）

## 变异验证（8 处，全部被抓）

| # | 变异 | 命中的用例 |
|---|---|---|
| 1 | 合并条件去掉 id 比较（不同照片也合并） | 不同照片不合并 |
| 2 | 去掉容量淘汰 | 深度上限 50 |
| 3 | push 不清空重做栈 | 新操作清空重做栈 |
| 4 | 摘要取栈底而非栈顶 | 不同照片不合并（断言 undoSummary） |
| 5 | 批量逐张压栈 | 整批只压一条命令 |
| 6 | 忽略取消标志 | 中途跳过剩余 |
| 7 | 撤销/重做方向互换 | 三张逐层回退 |
| 8 | Shift+Z 不识别为重做 | Ctrl+Shift+Z 重做 |
