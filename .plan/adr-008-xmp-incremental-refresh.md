# ADR-008：XMP 增量导入与冲突裁决

- 日期：2026-10-18
- 状态：已采纳
- 相关：报告 `docs/lumen-benchmark-2026-10-18.md` §5.7、FR-08（能力表第 13 行、§8.2 第 669 行）
- 参考实现：`lumen-raw/lumen/catalog.py:380-410`（ExifTool 批量读）、`commands.py:293-298`（`library.read_xmp`）

## 背景

扫描时会读 XMP，但**运行期间不监听外部变化**。用户在 Lightroom 改完评级切回来，
界面还是旧值，必须整个重扫 —— 10k 张要几十秒，而实际变化的往往只有个位数。

报告给的方向是「mtime 比对 + 只读变化的」。难点不在读，在**判**：

- 本应用可能还有未落盘的意图（`pending_xmp`，见 ADR-002），此时磁盘又被外部改了，
  谁赢？
- 升级用户第一次刷新时，所有 sidecar 都是「从未见过」的状态，若一律当成「已更新」，
  会弹出「已更新 10000 张」的假消息。
- 配了 RAW 目录但历史 sidecar 还在 JPG 旁边的相册，主路径的 sidecar 本来就不存在 ——
  当成「外部清空」会把 4 星变 0 星。

## 决策

### 1. 游标记在**侧边栏路径**上，粒度是毫秒

```sql
CREATE TABLE xmp_cursor (
  sidecar_path TEXT PRIMARY KEY,   -- 不是照片路径
  mtime_ms     INTEGER NOT NULL,
  rating       INTEGER NOT NULL,   -- 上次读到的内容
  flag         TEXT NOT NULL,
  label        TEXT NOT NULL,
  seen_at      TEXT NOT NULL
);
```

主键选 `sidecar_path`：一个分组的 RAW 与 JPG 各有一份 sidecar，而写盘只写主路径
（RAW 优先）。用照片路径做键会在「同一张照片换了主路径」时留下孤儿记录。

**必须是毫秒**。秒级 mtime 在「同一秒内写两次」时会被截断成同一个值，第二次改动被
静默跳过 —— 而这恰恰是「按 1 星、觉得不对、再按 3 星」的常见节奏。

### 2. mtime 只是预筛，内容才作数

mtime 变了但内容没变（外部只是重新保存了一次、或另一个程序 touch 了文件）时：
推进游标，**不打扰界面**（`unchanged += 1`）。

这一条把「增量」的收益和「不误报」的义务分开了：省的是解析，判的仍然是内容。

### 3. 没有游标就不猜

`cursor.is_none()` 且文件存在 → 只建立基线（`baselined += 1`），不产生「更新」。
否则升级用户第一次刷新会把全部照片报成「已更新」。

### 4. 无游标 + 文件不存在 = 无事发生

```
if mtime.is_none() && cursor.is_none() { unchanged += 1; continue; }
```

配了 RAW 目录但历史 sidecar 还在 JPG 旁边的相册，主路径的 sidecar 从来就不存在。
把它判成「外部删除」会让界面上的 4 星集体变 0 —— 这是**唯一**能一次性毁掉整库标记的
分支，所以它有一个专门的测试。

### 5. `decide` 三分支，冲突时游标**不前进**

```rust
pub fn decide(pending: Option<&CullState>, disk: &CullState) -> Decision {
    match pending {
        None => Decision::Adopt,
        Some(p) if p == disk => Decision::AlreadySynced,
        Some(_) => Decision::Conflict,
    }
}
```

`AlreadySynced` 是「上次其实写成功了，只是记录没删干净」—— 顺手清掉残留的 pending。

冲突**不推进游标**：下次刷新还要继续判，直到用户裁决。若在冲突时推进游标，用户
「这次先不管」之后就再也看不到这条冲突了。

### 6. 写盘成功后立刻推进游标，且记**磁盘实际值**

`DiskSink::write` 成功 → `upsert_xmp_cursor`。关键细节：reject 会写成 `Rating=-1`，
读回来是 **0 星**；照抄 `intent.rating` 会让游标与磁盘长期不一致，下次 mtime 一变
就误报「外部把 5 星改成 0 星」。

```rust
let disk_rating = if intent.flag == "reject" { 0 } else { intent.rating };
```

### 7. 旗标来源不新造第二套

沿用扫描的 `cullstore::resolve_flag`（本地 store 优先、JPG 侧兜底、`Rating=-1` 最高
优先）。刷新是「另一条读路径」，读出来的旗标必须与扫描逐字一致，否则同一张照片在
「刚扫完」和「切回窗口后」会显示成两个状态。

### 8. 并行 stat，但只碰元数据

10k 张串行 stat 在 Windows 上要 1 秒以上。`probe_mtimes` 用 `std::thread::scope` 分块
并行，线程数 `clamp(1, 8)`。这一步只读元数据、没有写操作，可以放心并行；**解析**仍
串行 —— 读变了的那些通常个位数，并发带来的复杂度不值。

### 9. 触发点是「窗口重新聚焦」+ 600ms 防抖，不是定时器

外部改动只可能发生在用户切走之后，切回来正是「该看一眼磁盘」的时刻。定时轮询会在
用户什么都没做的 10k 张目录上反复 stat。

防抖 600ms 合并 alt-tab 抖动，同时给外部程序落盘的时间：从 Lightroom 切回来时 XMP
可能正在被写，立刻 stat 会读到旧 mtime。

监听用 DOM 的 `window focus` 而不是 Tauri 的 `onFocusChanged`：WebView 的 window 在
应用窗口重获焦点时同样会收到，行为一致且不需要额外 ACL 授权。

### 10. 手动入口不置灰，而是当场解释

FR-09 要求「禁用按钮必须有常驻原因」，而顶栏没有位置常驻一整句「正在扫描照片，
暂时不能读取 XMP」。所以「读 XMP」按钮**不因互斥而禁用**，点击时若被挡就弹一句
原因（`refreshNow` 的 `auto=false` 分支）。留一个可点的按钮 + 即时解释，比留一个
灰按钮 + 无处安放的原因更诚实。

只有「正在读盘」时禁用 —— 那是防重复点击，不是互斥。

### 11. 冲突弹窗：默认保留本地，且默认值可见

三种选法都在同一个弹窗里：逐张二选一（默认「保留本地」）、「全部保留本地」、
「全部采用外部」。批量按钮只是把每行开关拨到同一侧，**不直接提交**。

默认选「保留本地」而不是「采用外部」：用户的标记是他刚做的动作，默认丢掉它比默认
保留它更伤人。但默认值不等于替用户决定 —— 不点「应用」就一个字节都不写，取消/关窗
都只是关掉（「不自动覆盖」的另一半是「不自动保留」）。

`use-external` 提交时把弹窗里显示的 `external` 一并回传：后端据此推进游标，**不重读
磁盘**。用户裁决的是他**看到的**那个值，弹窗开着时外部又改了一次不该改写这次裁决。

### 12. 选择按「路径 + 两侧的值」做键，失败项留在列表里

只按路径存会在两种情况下出错：同一张的外部值被新的刷新换掉（旧选择配新值，等于
用户裁决了他没看过的内容）；只按数组下标存，则会在部分裁决失败、列表变短时把选择
错位到别人头上。

`ResolveReport.failed` 是结构化的 `{ path, message }` 而不是 `"path: msg"` 字符串：
Windows 路径里的 `:` 会让前端解析变成猜。

弹窗只在**待裁决集合真的空了**时关闭。写失败的（磁盘没改，用户该再选一次）与这一批
压根没提交的，都必须留着。

重置选择放在**关闭时**而不是打开时：`isOpen` 由 false 变 true 的那一帧，重置 effect
是被动副作用，可能在用户点击之后才执行 —— 刚点的选择被无声抹掉。

### 13. 刷新进互斥表（`Activity::Refresh`）

刷新会读、裁决还会写同一批 sidecar，与扫描/导出/写盘并发会让「谁最后写」不可预测。
后端 5 种活动、前端 8 种，与除 `thumbnail` 外的所有长任务互斥（缩略图读的是内嵌
预览，两边不碰同一个文件）。

刷新**自己**也登记（`begin('refresh')`），否则导出按钮的禁用原因里看不到「正在读取
XMP」。

### 14. 与 `check_cull_state_cmd` 的分工

| | 比什么 | 量 | 触发 |
|---|---|---|---|
| `check_cull_state_cmd` | **内容** | 一条命令的几张 | 撤销/重做前 |
| `refresh_from_xmp_cmd` | **mtime 预筛 + 内容确认** | 整个集合 | 聚焦 / 手动 |

不合并：撤销前必须精确且量小，聚焦触发量大且允许「mtime 一致就跳过」。合并会让撤销
路径被 10k 张拖慢。

## 代价与风险

- **mtime 精度依赖文件系统**。NTFS 是 100ns，FAT32 是 2s —— 在 FAT32 的 U 盘上，
  「同一 2 秒内两次写」仍可能被跳过。已知未处理；触发条件是「用 U 盘当工作盘」，
  概率极低，且下一次任何改动都会让 mtime 越过窗口。
- **游标与真实磁盘可能长期不一致**：外部程序若把 mtime 改回旧值（`touch -d`），
  增量会漏掉那次改动。不做内容哈希校验 —— 10k 张全量哈希比全量重读还贵。
- **冲突粒度是「整张照片」**，不是逐字段合并。外部改了星级、本地改了色标也会算冲突。
  报告明确建议第一版不做逐字段合并，这里照办。
- **刷新期间的界面是「旧值」**。10k 张的 stat 约 0.3s，用户可能在这一瞬间点走。不做
  乐观更新 —— 读盘的结果就是真值，提前猜反而要处理「猜错再改回」的抖动。
- 前端 `groupPath()` 与后端 `primary_photo_path()` 必须逐字一致，跨语言无法共享。
  两边各有注释指认对方，改一处必须改两处。
